     1. Короткий опис системи
     Energy Monitor — це програмна система для персонального контролю споживання електроенергії. Система дозволяє користувачеві вести облік побутових електроприладів, задавати тарифи на електроенергію, додавати записи споживання, створювати ліміти, переглядати прогрес за лімітами та аналізувати витрати за допомогою звітів.
     У попередніх роботах було реалізовано backend системи, мобільний застосунок та web-інтерфейс. Backend побудовано на Node.js та Express, для роботи з базою даних використовується Sequelize та MySQL. Авторизація виконується за допомогою JWT-токенів, тому сервер не зберігає сесійний стан користувача в оперативній пам’яті.
     У межах цієї роботи показано, як backend системи можна масштабувати для роботи з більшим навантаженням. Для цього було реалізовано горизонтальне масштабування, де одночасно запускається декілька однакових копій backend-сервера, а запити між ними розподіляє Nginx load balancer.

     2. Мета та призначення масштабування backend
     Метою роботи є демонстрація можливості масштабування backend-частини системи Energy Monitor для обробки більшої кількості одночасних HTTP-запитів. Масштабування потрібне для випадків, коли кількість користувачів або інтенсивність запитів зростає, а один серверний процес вже не забезпечує необхідну продуктивність.
     У роботі використано горизонтальне масштабування. Це означає, що замість збільшення ресурсів одного сервера запускається кілька однакових backend-інстансів. Кожен інстанс виконує ті самі функції, серед яких, приймання HTTP-запитів, перевірка JWT-токену, запити до бази даних, виконання бізнес-логіки та повернення відповіді клієнту.
     Для перевірки ефективності масштабування було проведено навантажувальне тестування за допомогою k6. Тестування виконувалося для конфігурацій з одним, двома та трьома backend-інстансами. Результати використовуються для аналізу зв’язку між кількістю серверних копій і кількістю запитів на секунду, яку може обробити система.
     3. Обрана стратегія масштабування системи
     Для системи Energy Monitor було обрано горизонтальне масштабування backend-сервера. Обрана архітектура складається з таких основних елементів:
• клієнт або навантажувальний тест,
• Nginx load balancer,
• декілька backend-інстансів,
• спільна база даних MySQL,
• Docker volume для збереження резервних копій.
     Клієнт не звертається напряму до конкретного backend-інстанса. Усі запити надходять на Nginx, який працює на порту 8080. Nginx передає запити до backend-контейнерів, що працюють на внутрішньому порту 3001. Усі backend-контейнери підключаються до однієї бази даних MySQL, тому незалежно від того, який інстанс обробив запит, користувач працює з тими самими даними.
     Така стратегія підходить для системи Energy Monitor, оскільки backend є stateless. Стан користувача не зберігається в пам’яті конкретного процесу, а авторизація базується на JWT. Тому будь-який backend-інстанс може обробити будь-який запит користувача.

     4. Архітектура масштабованого backend
     Архітектура масштабованого backend побудована на Docker Compose. У контейнерах запускаються MySQL, Nginx та один або декілька backend-інстансів. Масштабування виконується командою docker compose up з параметром --scale backend=N, де N - кількість копій backend-сервера.
     Для демонстрації балансування було додано endpoint /instance. Він повертає hostname контейнера, який обробив конкретний запит. Якщо при багаторазовому зверненні до /instance повертаються різні значення, це означає, що запити реально розподіляються між різними backend-інстансами.

     5. Технічні рішення, які роблять масштабування можливим
     Масштабування backend стало можливим завдяки кільком технічним рішенням. По-перше, backend не зберігає стан користувача у пам’яті конкретного процесу. Після входу користувач отримує JWT-токен, який передається в кожному захищеному запиті. Через це будь-який backend-інстанс може перевірити токен і обробити запит без прив’язки до попереднього інстанса.
     По-друге, усі основні дані зберігаються в MySQL. Це означає, що backend-контейнери не мають власних окремих локальних даних, які могли б відрізнятися між інстансами. Такий підхід дозволяє запускати кілька копій backend і працювати з єдиним джерелом даних.
     По-третє, для резервних копій використовується окремий Docker volume. Це важливо, оскільки в системі є функція створення backup-файлів. Якщо backup-файли зберігалися б тільки всередині конкретного контейнера, при масштабуванні або перезапуску інстанса могли б виникнути проблеми з доступом до цих файлів. Тому у docker-compose.yml налаштовано спільний volume backend_backups.
     По-четверте, перед backend встановлено Nginx. Він приймає запити клієнтів і перенаправляє їх до доступних backend-контейнерів. У конфігурації використовується upstream backend_pool та алгоритм least_conn, що дозволяє направляти запити до інстанса з меншою кількістю активних з’єднань.
     6. Конфігурація Docker та Nginx
     Для контейнеризації backend було створено Dockerfile. Він використовує образ node:22-alpine, встановлює залежності через npm install, копіює код застосунку та запускає сервер командою npm start.
FROM node:22-alpine

WORKDIR /app

COPY package*.json ./

RUN npm install

COPY . .

EXPOSE 3001

CMD ["npm", "start"]
     
     У docker-compose.yml описано три основні сервіси: mysql, backend та nginx. Сервіс backend можна масштабувати через параметр --scale. Сервіс nginx відкриває порт 8080 назовні та перенаправляє запити до backend_pool. MySQL зберігає дані системи та має healthcheck, щоб backend запускався після готовності бази даних.

     Конфігурація Nginx містить upstream backend_pool, у який входить сервіс backend. Docker Compose при масштабуванні створює кілька контейнерів цього сервісу, а Nginx розподіляє між ними HTTP-запити.
events {}

http {
    upstream backend_pool {
        least_conn;
        server backend:3001;
    }

    server {
        listen 80;

        location / {
            proxy_pass http://backend_pool;
            proxy_http_version 1.1;

            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }
}

     7. Навантажувальне тестування
     Для навантажувального тестування використано інструмент k6. Тестовий сценарій створює 50 віртуальних користувачів протягом 30 секунд. Кожна ітерація виконує два HTTP-запити: GET /health та GET /instance. Перший endpoint перевіряє доступність backend, другий endpoint показує, який саме backend-інстанс обробив запит.
     Такий сценарій дозволяє перевірити роботу load balancer без впливу складної бізнес-логіки або запитів до бази даних. Це дає змогу окремо оцінити масштабування HTTP-шару backend та Nginx.
import http from "k6/http";
import { check, sleep } from "k6";

export const options = {
    vus: 50,
    duration: "30s"
};

export default function () {
    const health = http.get("http://localhost:8080/health");

    check(health, {
        "health status is 200": (res) => res.status === 200
    });

    const instance = http.get("http://localhost:8080/instance");

    check(instance, {
        "instance status is 200": (res) => res.status === 200,
        "instance has ok true": (res) => res.json("ok") === true
    });

    sleep(0.1);
}

     Для тестування використовувалися такі команди:
docker compose down
docker compose up -d --scale backend=1
docker compose ps
k6 run load-tests/k6-health.js

docker compose down
docker compose up -d --scale backend=2
docker compose ps
k6 run load-tests/k6-health.js

docker compose down
docker compose up -d --scale backend=3
docker compose ps
k6 run load-tests/k6-health.js

     8. Аналіз результатів навантажувального тестування
     За результатами тестування було отримано три набори показників для різної кількості backend-інстансів. Основними метриками для порівняння були кількість HTTP-запитів за секунду, p95 latency та частка помилкових запитів. Метрика http_reqs показує загальну кількість HTTP-запитів, які система обробила за одиницю часу. Метрика p95 latency показує, що 95% запитів були оброблені не повільніше за вказане значення. Метрика http_req_failed показує частку запитів, які завершилися помилкою.

Це означає, що після додавання другого backend-інстанса система почала впиратися вже не в кількість backend-процесів, а в інші ресурси локального середовища. При цьому кількість помилкових запитів у всіх трьох тестах залишалася на рівні 0.00%, тобто система зберігала коректну роботу навіть під навантаженням.
     9. Аналіз вузьких місць
     Першим ресурсом, який може вичерпуватися при навантаженні, є CPU backend-контейнерів. Якщо backend виконує складні обчислення або обробляє багато JSON-запитів, один Node.js процес може стати вузьким місцем. Горизонтальне масштабування дозволяє розподілити це навантаження між кількома процесами.
     Другим потенційним вузьким місцем є Nginx load balancer. У поточній роботі всі запити проходять через один Nginx-контейнер, тому при дуже великому навантаженні саме він може обмежувати загальну пропускну здатність.
     Третім вузьким місцем є база даних MySQL. У тестовому сценарії використовувалися легкі endpoint-и /health та /instance, які майже не навантажують базу даних. Але у реальних сценаріях, наприклад під час формування звітів або масового запису споживання, MySQL може стати основним обмеженням. У такому випадку додатково потрібно оптимізувати індекси, налаштовувати пул з’єднань, кешування або масштабування бази даних.
     Четвертим обмеженням є локальне середовище тестування. Docker Desktop працює через WSL, а всі запити виконуються через localhost. Тому результати тестування демонструють принцип масштабування, але не є абсолютними показниками продуктивності для production-середовища.
     10. Діаграма архітектури масштабування
     Для візуалізації масштабованої архітектури було підготовлено UML Component Diagram. На діаграмі показано, що клієнт або інструмент навантажувального тестування k6 надсилає HTTP-запити не напряму до backend-сервера, а до Nginx Load Balancer. Nginx приймає вхідні запити на порту 8080 та розподіляє їх між кількома однаковими backend-інстансами, які працюють у Docker-контейнерах.
     Кожен backend-інстанс виконує однакову бізнес-логіку Node.js/Express-застосунку та може обробити будь-який запит користувача, оскільки стан сесії не зберігається всередині конкретного сервера. Авторизація реалізована через JWT, а основні дані зберігаються у спільній MySQL-базі даних. Для резервних копій використовується спільний Docker volume, завдяки чому файли backup не залежать від конкретного backend-контейнера.

     11. Діаграма процесу навантажувального тестування
     Для опису послідовності проведення експерименту було підготовлено UML Activity Diagram. Вона показує порядок запуску середовища, масштабування кількості backend-інстансів та виконання навантажувального тестування.

     12. Висновки
     У ході виконання роботи було реалізовано горизонтальне масштабування backend-частини системи Energy Monitor. Backend було контейнеризовано за допомогою Docker, а для запуску інфраструктури використано Docker Compose. У системі було розгорнуто MySQL, Nginx load balancer та декілька backend-інстансів.
     Для перевірки балансування було додано endpoint /instance, який повертає ідентифікатор контейнера, що обробив запит. За допомогою багаторазових запитів було підтверджено, що Nginx розподіляє навантаження між різними backend-інстансами.
     Навантажувальне тестування виконано за допомогою k6. Було протестовано конфігурації з одним, двома та трьома backend-інстансами. Результати показали, що перехід з одного до двох інстансів збільшив кількість оброблених HTTP-запитів за секунду та зменшив latency. При переході до трьох інстансів приріст майже зупинився, що дозволило зробити висновок про появу інших вузьких місць, зокрема Nginx, локального середовища Docker Desktop/WSL, мережевого стеку та обмежень тестового сценарію.
     Таким чином, у роботі було показано, що backend системи Energy Monitor може масштабуватися горизонтально, а збільшення кількості backend-інстансів дозволяє підвищити пропускну здатність системи до моменту, коли обмеження починають виникати в інших компонентах інфраструктури.
