     1. Короткий опис проєкту
     Energy Monitor — це програмна система для персонального контролю споживання електроенергії. Вона призначена для користувачів, які хочуть бачити реальну картину власного енергоспоживання, контролювати витрати за тарифами, створювати ліміти та аналізувати історію споживання за допомогою звітів.
     Основна ідея проєкту полягає в тому, щоб об’єднати в одній системі облік електроприладів, тарифів, записів споживання, обмежень за періодами та аналітичних звітів. Система допомагає зрозуміти, які прилади можуть створювати найбільші витрати, як змінюється споживання з часом і коли користувач наближається до встановленого ліміту.
     Проєкт реалізовано як цілісну систему, що складається з backend API, мобільного застосунку, web-кабінету користувача, адміністративного web-інтерфейсу та конфігурації для демонстрації горизонтального масштабування backend. Клієнтські застосунки не працюють з базою даних напряму, а взаємодіють із серверною частиною через REST API.
     2. Складові частини системи
     Система Energy Monitor має модульну структуру. Backend виконує роль центрального ядра. Він обробляє запити, перевіряє JWT-токени, реалізує бізнес-логіку, працює з MySQL-базою даних і формує звіти. Мобільний застосунок забезпечує доступ звичайного користувача зі смартфона. Web-застосунок має і кабінет користувача і адміністративну панель.
     Окремо було реалізовано інфраструктурну частину для масштабування backend. Для цього використано Docker Compose, Nginx Load Balancer, окремий MySQL-контейнер і декілька backend-інстансів, між якими розподіляються HTTP-запити.

     3.1. Backend API
     Backend API є центральною частиною системи. Він забезпечує реєстрацію та вхід користувачів, видачу JWT-токена, перевірку ролей, роботу з тарифами, приладами, записами споживання, лімітами та звітами. Адміністративні маршрути винесені окремо, що дозволяє розділити доступ звичайного користувача та адміністратора. Реалізовано:
• авторизація та автентифікація користувачів через JWT;
• CRUD-операції для тарифів, електроприладів, записів споживання та лімітів;
• автоматичний розрахунок вартості споживання за активним тарифом;
• розрахунок прогресу за лімітами та статусів перевищення;
• формування зведених, щоденних, приладових та лімітних звітів;
• адміністративні маршрути для користувачів, аудиту та системних даних.

     3.2. Мобільний застосунок
     Мобільний застосунок реалізовано для звичайного користувача. Він дозволяє виконувати основні дії зі смартфона. Увійти в систему, переглянути загальний стан, керувати тарифами, приладами, споживанням, лімітами та переглядати звіти. Токен користувача зберігається локально, тому після повторного запуску застосунок може відновити сесію. Реалізовано:
• екран входу та реєстрації;
• збереження JWT-токена після авторизації;
• головний екран з оглядом даних;
• створення, редагування та видалення тарифів;
• створення, редагування та видалення електроприладів;
• додавання споживання вручну або за часом роботи приладу та його редагування;
• створення лімітів і перегляд прогресу;
• перегляд звітів за обраний період.

     3.3. Web-кабінет користувача
     Web-кабінет користувача реалізує ті самі основні користувацькі сценарії, але у браузері. Після входу користувач потрапляє до персонального кабінету, де доступні розділи огляду, тарифів, приладів, споживання, лімітів і звітів. Доступ до сторінки захищений перевіркою JWT-токена та ролі користувача. Реалізовано:
• персональний dashboard із короткою статистикою;
• робота з тарифами та активним тарифом;
• облік електроприладів та їх орієнтовної потужності;
• додавання й редагування записів споживання;
• створення лімітів за тиждень, місяць, рік або власний період;
• формування звітів за періодом, днями, приладами та лімітами.

     3.4. Адміністративний web-інтерфейс
     Адміністративний інтерфейс призначений для керування системою. Його функції недоступні звичайному користувачу. Після входу система перевіряє роль користувача, і тільки адміністратор може перейти до відповідної сторінки. Реалізовано:
• перегляд загальної статистики системи;
• пошук і фільтрація користувачів;
• зміна ролей користувачів;
• блокування та розблокування акаунтів;
• перегляд журналу аудиту;
• керування системними налаштуваннями;
• експорт та імпорт даних у JSON;
• створення резервних копій.

     3.5. Системні дані, експорт, імпорт і backup
     Для адміністратора було реалізовано розділ керування системними даними. У ньому можна змінювати базові налаштування системи, експортувати дані у JSON-файл, імпортувати їх назад та створювати резервні копії. Експортований файл містить службову інформацію, налаштування та дані основних таблиць.
     Імпорт підтримує два режими: merge та replace. Режим merge об’єднує імпортовані дані з поточними, а replace використовується для повного відновлення стану системи з резервної копії. Дії адміністратора фіксуються в журналі аудиту.

Рис. 3.8 – Керування системними даними

     3.6. Локалізація
     У web-частині реалізовано підтримку української та англійської мов. Тексти інтерфейсу винесені у словники, а динамічне формування підписів відбувається через функцію перекладу. Також використовуються механізми Intl.DateTimeFormat та Intl.NumberFormat для коректного форматування дат, часу та чисел відповідно до вибраної локалі.
     Для сортування текстових значень використовується localeCompare, що дозволяє враховувати мовні особливості. Для введення тексту застосовується підтримка напряму введення, що робить інтерфейс більш універсальним.

     3.7. Масштабування backend
     Для демонстрації масштабування backend було реалізовано горизонтальне масштабування через Docker Compose та Nginx Load Balancer. Кількість backend-інстансів задається параметром --scale backend=N. Усі backend-контейнери виконують однакову логіку, працюють зі спільною MySQL-базою та не зберігають стан сесії всередині конкретного процесу.
     Для перевірки балансування було додано endpoint /instance, який повертає ідентифікатор контейнера, що обробив запит. Навантажувальне тестування виконувалося за допомогою k6. Результати показали приріст пропускної здатності при переході з одного backend-інстанса до двох.
