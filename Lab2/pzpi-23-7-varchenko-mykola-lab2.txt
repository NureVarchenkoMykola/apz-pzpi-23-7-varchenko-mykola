1. Короткий опис системи
     Energy Monitor — це програмна система для персонального контролю споживання електроенергії. Система дозволяє користувачеві вести облік побутових електроприладів, задавати тарифи на електроенергію, додавати записи споживання, створювати ліміти, переглядати прогрес за лімітами та аналізувати витрати за допомогою звітів.
     У межах цієї лабораторної роботи було розроблено мобільний застосунок для Android мовою Kotlin з використанням Jetpack Compose. Мобільний застосунок є клієнтською частиною системи і взаємодіє з серверною частиною через REST API. Авторизація користувача виконується за допомогою JWT-токена, який зберігається на пристрої у SharedPreferences.
2. Мета та призначення мобільного застосунку
     Метою розробки мобільного застосунку є забезпечення зручного доступу користувача до основних функцій системи Energy Monitor зі смартфона. Застосунок призначений для звичайного користувача, тому в ньому реалізовано функції персонального керування власними даними, без адміністративного інтерфейсу.
     Мобільний застосунок дозволяє виконувати основні операції з даними користувача, а саме реєстрацію та вхід, перегляд поточної статистики, CRUD-операції для тарифів, приладів, записів споживання та лімітів, а також перегляд звітів. Адміністративні функції, такі як керування користувачами, блокування облікових записів або перегляд журналу аудиту, навмисно не включені до мобільного застосунку, оскільки вони мають бути реалізовані у Web-інтерфейсі адміністратора.
     
     
3. Прийняті інженерні рішення
3.1. Платформа та технології
     Для реалізації мобільного застосунку обрано платформу Android та мову програмування Kotlin. Інтерфейс користувача побудовано з використанням Jetpack Compose, що дозволяє створювати декларативний UI без використання XML-макетів. Такий підхід спрощує підтримку екранів, повторне використання компонентів і роботу зі станом інтерфейсу.
     Для взаємодії з серверною частиною використано бібліотеку Retrofit. Вона забезпечує опис HTTP-запитів через інтерфейс ApiService та автоматичне перетворення JSON-даних у Kotlin data class-моделі за допомогою Gson Converter. Для перегляду мережевих запитів під час розробки використовується OkHttp Logging Interceptor.
3.2. Архітектура застосунку
     Структура мобільного застосунку поділена на окремі пакети: data, ui, components, screens, utils та theme. Пакет data містить API-клієнт, моделі даних і механізм збереження токена. Пакет ui містить екрани застосунку, спільні UI-компоненти, утиліти перевірки введення та тему оформлення.
     Головна активність MainActivity не містить бізнес-логіки. Вона лише запускає Compose-інтерфейс і передає керування компоненту EnergyMonitorApp. Такий підхід зменшує зв’язність коду та робить застосунок зручнішим для подальшого розширення.
3.3. Авторизація та збереження сесії
     Після успішного входу сервер повертає JWT-токен. Мобільний застосунок зберігає цей токен у SharedPreferences через клас TokenManager. При наступному запуску застосунок перевіряє наявність токена і, якщо він є, одразу відкриває головний екран без повторної авторизації. Вихід із системи очищує збережений токен.
     Усі запити до захищених endpoint-ів виконуються з HTTP-заголовком Authorization у форматі Bearer token. Якщо сервер повертає помилку авторизації, користувач отримує повідомлення через Snackbar.
3.4. Обробка помилок та валідація
     У застосунку реалізовано два рівні обробки помилок. Помилки введення користувача відображаються безпосередньо під відповідними полями форми. Наприклад, якщо користувач вводить некоректну дату або нечислове значення у поле потужності, під полем з’являється пояснення помилки.
     Помилки, отримані від backend API, відображаються через Snackbar. Наприклад, якщо користувач намагається створити ліміт, який перетинається з уже існуючим лімітом такого ж типу, сервер повертає код 409, а застосунок показує повідомлення про конфлікт даних.
3.5. Оформлення інтерфейсу
     Інтерфейс застосунку оформлено з використанням власної кольорової теми. Основними кольорами є зелений, синій, світло-м’ятний та світлий фон. Для основних блоків використано картки з округленими кутами, градієнтні заголовки екранів, окремі кнопки дій і сітку статистики. Такий дизайн відрізняється від стандартного шаблону Android Studio і краще відповідає тематиці енергомоніторингу.
4. Опис екранів мобільного застосунку
4.1. Екран авторизації
     Екран авторизації дозволяє користувачу увійти до системи або створити новий обліковий запис. Користувач вводить email та пароль. Для обох полів реалізована перевірка. Email не може бути порожнім і повинен мати коректний формат, а пароль не може бути порожнім і повинен містити не менше шести символів.
     Після реєстрації користувач отримує повідомлення про успішне створення акаунта і може виконати вхід. Після входу застосунок зберігає JWT-токен і переходить на головний екран.

4.2. Головний екран
     Головний екран є стартовим екраном після авторизації. На ньому відображається загальне привітання, короткий звіт за поточний місяць, блок оповіщень за лімітами, статистика кількості тарифів, приладів, записів споживання та лімітів, а також список останніх записів споживання.
     З головного екрана користувач може перейти до розділів «Тарифи», «Прилади», «Споживання», «Ліміти» та «Звіти». Також доступні кнопки оновлення даних і виходу з облікового запису. На головному екрані не відображаються технічні дані на кшталт user id або role, оскільки вони не потрібні звичайному користувачу.

4.3. Екран тарифів
     Екран тарифів призначений для керування тарифами користувача. На ньому реалізовано повний набір CRUD-операцій. Доступні створення нового тарифу, перегляд списку тарифів, редагування існуючого тарифу та видалення тарифу. Окремо реалізовано можливість зробити існуючий тариф активним.
     Форма тарифу містить назву тарифу, ціну за кВт*год, дату початку дії, необов’язкову дату завершення та перемикач активності. При створенні або редагуванні застосунок перевіряє, що назва не порожня, ціна є додатним числом, а дати мають формат YYYY-MM-DD. Якщо дата завершення вказана, вона не може бути раніше дати початку.

4.4. Екран приладів
     Екран приладів дозволяє користувачу вести список електроприладів, для яких у подальшому можна додавати записи споживання. Для кожного приладу зберігається назва, опис і орієнтовна потужність у кВт.
     На екрані реалізовано створення, перегляд, редагування та видалення приладів. Назва приладу є обов’язковою. Потужність не є обов’язковою, однак якщо користувач її вводить, значення повинно бути додатним числом. Потужність використовується при розрахунку споживання за часом роботи приладу.

Рис.4.7 – Редагування приладу

4.5. Екран споживання
     Екран споживання призначений для керування записами фактичного використання електроенергії. Користувач може створювати записи двома способами: вручну ввести кількість кВт*год або вибрати прилад і вказати час його роботи. У другому випадку сервер розраховує споживання на основі потужності приладу та кількості годин.
     Для кожного запису вказується дата, необов’язковий прилад, значення споживання або час роботи, а також нотатки. На екрані доступні перегляд історії записів, редагування та видалення записів. При редагуванні запис підставляється у форму, після чого користувач може змінити дані і зберегти зміни.
     Валідація форми перевіряє правильність формату дати, додатність числових значень, а також наявність приладу при розрахунку за часом. Якщо для вибраного приладу не задана потужність, застосунок повідомляє користувача, що такий спосіб розрахунку неможливий.

Рис.4.9 – Додавання споживання
4.6. Екран лімітів
     Екран лімітів дозволяє користувачу створювати обмеження на споживання електроенергії за певний період. Підтримуються типи періодів week, month, year та custom. Для week, month і year дата завершення розраховується сервером автоматично, а для custom користувач задає дату завершення вручну.
     Для ліміту задається значення у кВт*год, тип періоду, дата початку, дата завершення для custom-періоду, поріг попередження у відсотках та параметр відображення попереджень. На екрані реалізовано створення, перегляд, редагування та видалення лімітів.
     Для кожного ліміту застосунок завантажує прогрес. Скільки використано кВт*год, відсоток використання, статус досягнення порога та факт перевищення ліміту. Якщо ліміт перевищено або досягнуто поріг попередження, користувач бачить відповідний статус. Якщо показ попереджень вимкнено, статус ліміту все одно відображається в розділі лімітів, але не виводиться як активне попередження на головному екрані.

4.7. Екран звітів
     Екран звітів дозволяє переглядати аналітику за вибраний період. Користувач задає дату початку і дату завершення, після чого застосунок завантажує декілька видів звітів із backend API.
     На екрані відображається загальне зведення за період, щоденний звіт, звіт за приладами та звіт за лімітами. У звіті за лімітами технічні статуси backend API перетворюються на зрозумілі користувачу написи:
• ok – «у межах норми»,
• threshold_reached – «досягнуто поріг попередження»,
• limit_exceeded – «ліміт перевищено».

5. Взаємодія мобільного застосунку з іншими частинами системи
     Мобільний застосунок взаємодіє із серверною частиною через REST API. Серверна частина реалізована на Node.js та Express і працює з базою даних MySQL через Sequelize. Мобільний застосунок не звертається до бази даних напряму, а отримує і змінює дані тільки через API.
     Зв’язок між застосунком і сервером виконується за допомогою HTTP-запитів. Для локальної розробки Android-емулятор звертається до backend за адресою http://10.0.2.2:3001/. Усі захищені запити містять JWT-токен у заголовку Authorization.
     Основні групи API, що використовуються мобільним застосунком це auth, appliances, tariffs, consumption, limits та reports. Адміністративні API не використовуються у мобільному клієнті, оскільки вони призначені для Web-застосунку адміністратора.
5.1. Використані API endpoint-и
Група APIEndpoint-иПризначенняAuthPOST /api/auth/register, POST /api/auth/login, GET /api/auth/meРеєстрація, вхід, перевірка користувачаAppliancesGET/POST/PATCH/DELETE /api/appliancesCRUD електроприладів користувачаTariffsGET/POST/PATCH/DELETE /api/tariffs, POST /api/tariffs/{id}/activateCRUD тарифів і вибір активного тарифуConsumptionGET/POST/PATCH/DELETE /api/consumptionCRUD записів споживанняLimitsGET/POST/PATCH/DELETE /api/limits, GET /api/limits/{id}/progressCRUD лімітів і перегляд прогресуReportsGET /api/reports/summary, /daily, /by-appliance, /limitsАналітичні звіти

8. Висновки
     У ході виконання лабораторної роботи було розроблено мобільний застосунок для Android, який є частиною системи Energy Monitor. Застосунок взаємодіє з backend API, використовує JWT-авторизацію, зберігає токен користувача на пристрої та надає доступ до основних функцій системи.
     Було реалізовано окремі екрани для авторизації, головного огляду, тарифів, приладів, споживання, лімітів і звітів. Для основних сутностей користувача реалізовано повний набір CRUD-операцій.      Під час розробки було використано Kotlin, Jetpack Compose, Retrofit, SharedPreferences та власну тему оформлення. Код застосунку структуровано за пакетами, що спрощує підтримку і подальший розвиток системи.
